# 当前项目现状分析

## 当前代码结构与已有功能

- `legacy_quote_app.py`：约 2,030 行的 Tkinter 单文件桌面程序，包含报价录入、物料 Excel 导入、金额核算、PDF 生成、SMTP 邮件、草稿/历史恢复、撤销重做和本地配置。
- `quotation.db`：旧 SQLite 数据库，仅有 `quotations` 业务表，现存 3 条正式报价。
- `新建 Microsoft Excel 工作表.xlsx`：3 个工作表，仅 `Sheet1` 第 2 行有一条物料“DJI Mini4Pro随心换一年版 / 430”。
- `records/`：4 份历史报价 PDF；其中 `SRV-20260706-95CD8F.pdf` 未出现在旧数据库里。
- `config.json`：SMTP 和 PDF 显示配置，当前未发现实际密码。

## 可复用代码

- 报价项目保存历史价格快照的做法。
- SQLite 参数化查询、线程锁和旧表增量加列思路。
- PDF 生成的临时文件 + `os.replace` 原子替换。
- 用户输入 HTML/XML 转义、中文/英文分段排版思路。
- Excel 两列物料导入、PDF 二维码、异步邮件与主线程队列机制。
- 跨平台打开文件、日志轮转和配置默认值合并。

## 主要问题与高风险

- 所有层次集中在一个文件，界面、业务、数据库、PDF、邮件强耦合。
- 旧库没有客户、设备、工单、报价版本、库存流水、财务流水和附件等实体。
- 金额使用 SQLite `REAL` 和 Python `float`，存在二进制小数误差。
- `INSERT OR REPLACE` 会删除再插入同一唯一键记录，无法保证报价版本历史。
- 旧库允许直接删除报价，没有软删除、审计主体和完整状态历史。
- 配置中的 SMTP 授权码使用基于固定盐和机器名的 XOR 混淆，不属于安全加密；新系统不迁移密钥。
- 旧程序采用相对路径，启动目录变化会导致数据库、日志和 PDF 写入其他位置。
- PDF 使用 `STSong-Light` CID 字体；本机复核时一份孤立历史 PDF 大面积中文不可见，字体可移植性不足。
- 旧表时间为无时区文本；新系统统一按带时区时间处理，迁移数据只能保留原始文本语义。
- 旧 Excel 首行为空，Pandas 默认表头解析可能把唯一物料当成列名，存在导入丢行风险。

## 数据迁移风险与处理

- 旧报价不能被视为已收款，因此迁移报价和完成工单，但不自动生成收入流水。
- `sn` 中“无”“查询”等值不能作为真实唯一序列号，迁移为可追溯的临时设备编号。
- 旧配件没有采购成本，迁移后的历史毛利润无法从旧数据准确还原，成本记为 0 并写入报告。
- 一个未入库的 `SRV-...pdf` 作为孤立文件报告，不自动猜测客户或工单归属。
- 每次迁移前复制旧数据库到 `backups/`；不能映射的内容写入 `migration_reports/*.json`。
- 旧 `quotation.db` 和 `legacy_quote_app.py` 保持原样，新系统使用独立 `repair_management.db`。

## 本次实施步骤

1. 保留旧程序与旧库，建立模块化 FastAPI/SQLAlchemy 单体架构。
2. 建立完整业务实体、Alembic 基线迁移和安全旧库迁移脚本。
3. 实现客户、设备、工单、报价版本、库存、财务、附件、日志、回访等 API。
4. 实现浏览器管理端和工单集中工作台。
5. 实现三类 PDF、中文字体发现、原子替换与附件登记。
6. 实现插件式飞控日志解析、规则分析、企业微信/顺丰/标定 Mock。
7. 运行迁移、测试和端到端流程，修复实际错误并记录限制。
