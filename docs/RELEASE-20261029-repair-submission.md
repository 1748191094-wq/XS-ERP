# 维修申请：明确工单与附件提交结果

本轮从 39bebcf 接力，用户任务是完成维修申请并明确提交结果、下一步去哪里。原页面在创建工单后立即切换成功页，附件失败写在已隐藏的表单内，客户无法得知附件未成功；任一附件失败还会阻断剩余上传。

现在结果页分开呈现工单号、附件处理数量、逐项未确认结果及“查看服务进度”主操作。创建成功后将焦点移至结果标题；上传期间显示真实处理进度、禁用主跳转，单个失败继续后续上传。无附件和全部成功有独立反馈。移除原先无可靠接口支持的物流进度承诺。

设备/地址初始化增加加载、失败及重新读取；没有地址时解释寄修为何无法提交，提供“我的”地址入口和到店选项。提交失败继续保留表单输入。

## 设计依据（2026-10-29 查阅）

- https://developer.apple.com/design/human-interface-guidelines/entering-data ：说明必需信息、让用户知道为何无法继续，已知设备与地址复用现有数据。
- https://developer.apple.com/design/human-interface-guidelines/progress-indicators ：长操作应提供处理中反馈，区分已完成与仍在进行。
- Apple 官方 Markdown 版本通过上述地址加 `.md` 读取。实现适配现有 Web 品牌；沿用系统字体与明暗语义色，不添加玻璃或动效。

## 限制与后续

附件接口没有幂等或客户附件列表查询，网络断开无法确定服务端是否保存。结果使用“未能确认”，不盲目自动重传，不重复创建工单；提示联系门店核对或补充。尚无本页补传能力，附件文件状态仅保留在当前页面内。主操作上传期间禁用，但浏览器返回或其他导航仍可离开；未宣称离开后上传可靠继续。

测试全为隔离 fixtures，不是后端端到端验收。后台 A 整体验收仍待完成，B 未开始，Windows 与实机未验证。后续 UI 可继续检查维修申请长表单的分组、标签关联、离开页面输入保留，以及列表直达新工单。无数据库、真实设备、GitHub 或部署操作。
